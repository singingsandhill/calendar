trading 데이터 모델

코인 트레이딩 봇(빗썸, KRW-ADA)의 7개 테이블입니다. JPA 엔티티 기준이며 테이블은 Hibernate ddl-auto: update 가 만듭니다. JPA 연관관계가 하나도 없어서 DB FK 도 없고, 모든 참조는 id 값만 가지는 논리 참조입니다.

Fig. 1

신호 · 주문 · 포지션 + 시계열

위쪽 세 테이블이 매매 한 번의 흔적입니다. 매수는 체결 뒤 새 포지션과 같은 트랜잭션에서 저장되며 position_id 가 채워집니다. 매도는 처음부터 청산할 포지션을 가리킵니다. signal_id 는 신호로 일어난 매매에만 채워지고, 리스크 청산·리밸런싱·수동 매매에서는 null 입니다. 아래 네 테이블은 서로를 id 로 가리키지 않고 시간으로만 이어집니다. trading_daily_summaries 는 전날 청산된 포지션과 그날 첫·마지막 계좌 스냅샷으로 계산한 값입니다.

Database

DB 가 보장하는 것

  • FK 없음 — JPA 연관관계가 없어 signal_id·position_id 는 평범한 bigint
  • UQ — trading_trades.uuid, trading_candles (market, candle_date_time), trading_daily_summaries.summary_date
  • IDX — (market, 시간) 기간 스캔용 + trades.position_id 조회용 (FK 가 없어 인덱스를 따로 둠)

Application

코드가 보장하는 것

  • 매수 주문과 새 포지션은 한 트랜잭션에 저장 — TradingBotService
  • client_order_id 는 주문 전 선영속화 경로에서만 채워지는 멱등키 (nullable)
  • order_ratio 는 매수에만 채워짐 (ATR 기반 동적 비중)
  • 일일 요약은 00:01 에 전날 기준으로 생성 — ProfitService.generateDailySummary

Retention

보관

  • trading_candles 만 매일 자정에 90일 넘은 행 삭제 (candle-retention-days: 90)
  • 나머지 6개는 삭제 경로가 없어 계속 쌓임. trading_signals 는 루프 틱마다 1행 (하루 약 1,440행)
  • 스냅샷 deleteOlderThan 은 정의만 있고 호출처 없음
