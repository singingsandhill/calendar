Sequence · trading module

코인 봇 매매 시퀀스

코인 트레이딩 봇(빗썸, KRW-ADA)이 매분 한 번 도는 루프와, 그 안에서 매수 한 건이 나가는 경로입니다. 코드 기준이며 0–6 단계 번호는 TradingBotService.executeTradeLoop 주석의 번호를 따릅니다.

Fig. 1

1분 틱 — executeTradeLoop

CandleScheduler 가 매분 5초에 루프를 부릅니다. trading.bot.enabled=false 면 부르지 않고, 봇이 정지·일시정지 상태면 루프가 바로 끝납니다. 앞 네 단계는 순서가 고정입니다 — 0 결과 미확인(SUBMITTED) 주문 스윕, 1 1분봉 200개 동기화, 2 리스크 체크(열린 포지션마다 현재가로 손절·익절·트레일링 등을 판정하고 걸리면 시장가 매도), 3 신호 계산·저장. 그다음 이번 틱에 청산이 났거나(exit), 캔들 동기화가 실패했거나(stale), 신호가 없거나(null), 재시작 후 보호 전용 모드(recovery)면 매매 없이 끝납니다. 통과하면 |점수| ≥ 60 인 BUY/SELL 은 리밸런싱보다 먼저 신호 매매(4)로 가고, 아니면 리밸런싱(5)을 먼저 확인해 실행되지 않았을 때만 신호 매매(6)로 갑니다. 4·6 도 쿨다운 30분, 최대 포지션 2개, 매도 최소 보유 30분·최소 순익 조건을 다시 거칩니다. PAPER 모드에서는 청산·매매 주문이 거래소까지 가지 않고 API 클라이언트의 가상 체결에서 끝납니다(Fig. 2).

Fig. 2

매수 한 건 — executeBuy

Fig. 1 의 4·6 단계에서 BUY 가 나온 경우입니다. 서킷브레이커(연속 손실 3회 또는 당일 −5%)와 결과 미확인 주문을 먼저 보고, 잔고·현재가를 받아 물타기 차단과 코인 비중 상한(80%)을 확인한 뒤 ATR 로 주문 비중(15~35%)을 정해 0.5% 를 덜고 주문합니다. 현재가를 받지 못하면 가드를 건너뛰지 않고 매수를 막습니다. cid 를 쓰는 구성(v2, 또는 v1 + clientOrderIdEnabled)이면 주문 전에 Trade 를 SUBMITTED 로 먼저 저장합니다. 주문은 BithumbApiClient 의 모드 게이트를 지나며, 기본값 PAPER 에서는 현재가 +0.5% 에 메모리 안에서 체결합니다. 체결가를 얻으면 SL/TP 를 붙인 Position 과 체결된 Trade 를 TransactionTemplate 한 트랜잭션에 저장합니다 — 주문 HTTP 는 트랜잭션 밖에서 끝납니다. 매도(executeSell)도 같은 모양이고, SUBMITTED 행이 청산할 포지션을 가리킵니다.

Invariant

순서가 곧 안전장치

  • 리스크 체크(2)가 신호(3)보다 먼저 — 신호 쪽 예외·지연이 손절을 막지 못하게. 가드: riskCheckRunsBeforeSignalGeneration
  • 캔들 동기화가 실패해도 2·3 은 실행하고 4–6 만 막음 (리스크 판정은 캔들이 아니라 실시간 현재가)
  • 복구 모드 게이트는 3 직후·4 앞 — 보호는 돌리고 신규 매매만 막는 유일한 위치

Order path

주문 한 건의 안전장치

  • 주문 HTTP 는 트랜잭션 밖, Position + Trade 저장만 짧은 트랜잭션
  • 미해결 SUBMITTED 가 있으면 신규 매수 차단, 같은 포지션 미해결 매도가 있으면 재매도 차단
  • 스윕: 10초 grace 뒤 cid 재조회 — 체결이면 DONE + Position, 취소면 CANCEL, 2분 동안 못 찾으면 FAILED

Defaults

기본 구성

  • 모드 PAPER — LIVE 는 TRADING_BOT_MODE=LIVE 로만
  • 주문 API V1 + clientOrderIdEnabled=false — 선영속화가 꺼져 있어 스윕할 SUBMITTED 행이 생기지 않음
  • 시세·캔들 조회는 모드와 무관하게 실제 API
