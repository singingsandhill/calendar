datedate 데이터 모델

일정 서비스의 12개 테이블을 두 장으로 나눴습니다. JPA 엔티티를 기준으로 그렸고, 테이블은 Hibernate ddl-auto: update 가 생성합니다. 컬럼명은 Spring 기본 네이밍(snake_case)입니다.

Fig. 1

계정 · 소유 · 참여

왼쪽 일정 영역(로그인 없이 사용)은 schedules.owner_id·participants.schedule_id 가 DB FK 로 묶입니다. 오른쪽 카카오 로그인 영역은 user_id·schedule_id 를 FK 제약 없이 id 값으로만 가집니다. owners.user_id 는 nullable 이며, 로그인 사용자가 오너에 처음 연결될 때(first-claim) 채워집니다. user_activities.target_id 는 type 에 따라 일정·참여자·장소·메뉴 id 를 가리키는 다형 참조라 선으로 그리지 않았습니다.

Fig. 2

후보 · 투표

세 후보 테이블은 같은 구조입니다. 후보는 일정에 속하고, 후보마다 투표 테이블이 따로 있습니다. voter_name 은 participants 를 참조하는 FK 가 아니라 이름 문자열입니다. time_slots.day_index 는 participants.selections 와 같은 날짜 인덱스를 씁니다. 참여자 중 누군가 가능하다고 저장한 날만 후보로 받는데, 이는 DB 제약이 아니라 도메인 규칙(Schedule.hasAvailabilityOn)입니다.

Database

DB 가 보장하는 것

  • FK — schedules → owners, 일정 하위 4개 테이블 → schedules, 투표 3개 테이블 → 각 후보
  • UQ — schedules (owner_id, year, month), app_users.kakao_id, recap_shares.token, recap_shares (user_id, share_year)
  • IDX — user_activities (user_id, occurred_at) (연간 리캡 집계용)

Application

코드가 보장하는 것 (DB 제약 없음)

  • 일정당 참여자 최대 8명, 이름 중복 불가(대소문자 무시) — Schedule.addParticipant
  • 한 일정 안에서 장소·메뉴 이름과 시간대(day_index·start·end) 중복 불가 — 각 *Service 의 existsBy…
  • 후보 하나에 같은 투표자는 1표(대소문자 무시) — Location·Menu·TimeSlot.addVote
  • 활동 기록은 (user_id, type, target_id) 로 중복을 막음 — UserActivityService

Deletion

삭제 전파

  • 일정을 지우면 참여자·후보·투표가 JPA cascade(ALL + orphanRemoval)로 함께 삭제됨. DB FK 에는 ON DELETE 가 없음
  • user_activities·recap_shares 는 정리되지 않아, 삭제된 일정 id 가 남을 수 있음
  • owners·app_users 는 삭제 경로 없음
